# Architecture Decision Records

Short records of decisions that are easy to accidentally undo while making an
unrelated change. Each ADR is deliberately small. If a future change conflicts with one
of these, either the change is wrong or the ADR is outdated — update the ADR
explicitly rather than silently drifting away from it.

See `docs/SYSTEM_ARCHITECTURE.md` for the full current-implementation context these
decisions live in, and `docs/DOMAIN_GLOSSARY.md` for term definitions.

**Current implementation overlay (2026-08-27, ADR-0027).** B0.2, B0.3 and B0.4 are implemented
and locally verified.
Their architectural decisions remain unchanged.

training offline-capable after onboarding, and puts structured raw sporting data in the
cloud for Free. Its effect on earlier records, without reproducing their contents:

| [0018](0018-indexeddb-production-activation-fencing-and-outage-policy.md) | **Proposed. Incomplete design.** The attempted answer to ADR-0017 Decision 3's bundled prerequisite — resolves **neither** half. Decision 13 row 0b is narrowed, not closed: a proposed `localStorage` Activation Ledger, corrected to be established as a barrier *before* IndexedDB evidence finalizes (never as a best-effort write after), catches an ordinary witness loss while IndexedDB is unreachable. It is **not self-healing**. A targeted ledger deletion (making the ledger absent) does not by itself recreate row 0b while the witness remains present — it only removes this domain's future mitigation against a *later*, independent witness loss coincident with IndexedDB being unreachable; a whole-`localStorage`-origin wipe removes ledger and witness together in one action, directly recreating the original ambiguity the moment IndexedDB is unreachable. Ledger corruption is different again: an invalid or unreadable ledger fails closed (`invalid_activation_metadata` / `activation_ledger_unreadable`) and never silently selects `localStorage` — it costs availability, not safety. Row 0b stays bundled into ADR-0017 Decision 3 pending an explicit residual-risk decision — accepting that residual would resolve the pending governance decision, not technically eliminate the ambiguity itself; only unconditional fail-closed behavior would do that. Old-build/tab exclusion is **not resolved** either — a Web-Locks presence check, corrected to a single acquisition per tab (querying every historical lock-name version, fail-closed on any request/query failure, never a "safe no-op" when Web Locks is unavailable) plus an explicit, honest, unverifiable user confirmation (scoped to this browser's own storage partition, not other devices) is the best achievable design without a backend, and this ADR proves directly why no candidate (staged deployment, service worker, handshake, broadcast, Web Locks alone, a bare session registry, or the presence-check-plus-confirmation itself) can make already-running old JavaScript stop writing — a redesigned server-authoritative backend could make such writes non-authoritative, never prevent the local `localStorage.setItem` call itself.
