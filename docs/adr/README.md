# Architecture Decision Records

Short records of decisions that are easy to accidentally undo while making an
unrelated change. Each ADR is deliberately small. If a future change conflicts with one
of these, either the change is wrong or the ADR is outdated — update the ADR
explicitly rather than silently drifting away from it.

See `docs/SYSTEM_ARCHITECTURE.md` for the full current-implementation context these
decisions live in, and `docs/DOMAIN_GLOSSARY.md` for term definitions.

**Current implementation overlay (2026-08-27, ADR-0027).** B0.2, B0.3 and B0.4 are implemented
and locally verified.
Their architectural decisions remain unchanged.

| [0018](0018-indexeddb-production-activation-fencing-and-outage-policy.md) | **Proposed. Incomplete design.** The attempted answer to ADR-0017 Decision 3's bundled prerequisite — resolves **neither** half. Decision 13 row 0b is narrowed, not closed: a proposed `localStorage` Activation Ledger, corrected to be established as a barrier *before* IndexedDB evidence finalizes (never as a best-effort write after), catches an ordinary witness loss while IndexedDB is unreachable. It is **not self-healing**. A targeted ledger deletion (making the ledger absent) does not by itself recreate row 0b while the witness remains present — it only removes this domain's future mitigation against a *later*, independent witness loss coincident with IndexedDB being unreachable; a whole-`localStorage`-origin wipe removes ledger and witness together in one action, directly recreating the original ambiguity the moment IndexedDB is unreachable. Ledger corruption is different again: an invalid or unreadable ledger fails closed (`invalid_activation_metadata` / `activation_ledger_unreadable`) and never silently selects `localStorage` — it costs availability, not safety. Row 0b stays bundled into ADR-0017 Decision 3 pending an explicit residual-risk decision — accepting that residual would resolve the pending governance decision, not technically eliminate the ambiguity itself; only unconditional fail-closed behavior would do that. Old-build/tab exclusion is **not resolved** either — a Web-Locks presence check, corrected to a single acquisition per tab (querying every historical lock-name version, fail-closed on any request/query failure, never a "safe no-op" when Web Locks is unavailable) plus an explicit, honest, unverifiable user confirmation (scoped to this browser's own storage partition, not other devices) is the best achievable design without a backend, and this ADR proves directly why no candidate (staged deployment, service worker, handshake, broadcast, Web Locks alone, a bare session registry, or the presence-check-plus-confirmation itself) can make already-running old JavaScript stop writing — a redesigned server-authoritative backend could make such writes non-authoritative, never prevent the local `localStorage.setItem` call itself. ADR-0017 Decision 3 therefore remains blocked as a whole; no activation is recommended |

| [0022](0022-team-foundation-domain-and-persistence.md) | **Accepted. Corrected across subsequent independent review passes — see the ADR's own correction notes for the current, complete list.** Canonical product authority is `docs/TEAM_FOUNDATION_AND_ADMINISTRATION_BETA_SPECIFICATION.md`, which this ADR implements. `Profile.id` is its own UUID, linked 1:1 to a Supabase Auth account via `account_profile_links`, never equal to the auth user id; exactly three composable contextual functions (`team_admin`, `coach`, `training_lead`) with no Team Captain modeled; a new member may receive `team_admin` directly as part of accepting a complete invitation proposal, but an **already-active** member can only gain it by accepting a Team Admin Request — these are two distinct paths, not one rule with an exception; invitations use a hashed one-time token with replace-based (never in-place) revise/resend, each attributed to whichever admin actually created that specific invitation, not the team's founder; member email is exposed only via one narrow, admin-gated RPC, never a browsable column; team creation is pilot-gated and the optional `Athlete` capability is never auto-created; the five mutations that must also send email run through server-only Next.js Route Handlers (never the browser) calling a provider-neutral `EmailService` that never fabricates delivery success, with SMTP configuration validated strictly (no permissive coercion of a malformed port or secure flag) and a best-effort delivery-recording failure logged, never silently discarded; every RPC failure crosses the RPC/HTTP boundary as `'<kind>: <message>'`, re-parsed and re-sanitized by one function on both the direct-RPC and Route Handler paths (never a raw provider message passed through), mapped to a stable HTTP status, and failing closed to a non-leaking generic error for anything unrecognized; and the `TeamService` "never throws" contract is now enforced centrally by one wrapper (`withNeverThrows`) rather than left to each method's own care. **A second, independent review pass then found and closed:** a restore-vs-final-admin-exit race (`restore_team` now takes the same per-team advisory lock before its status transition, and `leave_team`/`relinquish_own_admin` now re-read Team status only after acquiring it); a Team-side Admin Request read method that relied solely on RLS rather than a genuinely admin-only RPC (`list_admin_requests_for_team`); `set_participation`/`assign_direct_function`/`remove_direct_function` writing without locking the target Membership row first; a function-array validation gap that silently accepted a NULL array and never rejected duplicates; the five email-sending Route Handlers having no exception boundary around a rejected (not merely resolved-error) RPC promise; and a signed-out recipient having no way to sign in from the invitation/Admin-Request overlay. **That last UI remedy was later superseded by B0.2e:** the optional `CloudSignInForm`/`AccountControl` cluster was retired, and the mandatory global identity gate now completes authentication and onboarding before any pending Team intent is replayed. |
