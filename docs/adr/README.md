# Architecture Decision Records

Short records of decisions that are easy to accidentally undo while making an
unrelated change. Each ADR is deliberately small. If a future change conflicts with one
of these, either the change is wrong or the ADR is outdated — update the ADR
explicitly rather than silently drifting away from it.

See `docs/SYSTEM_ARCHITECTURE.md` for the full current-implementation context these
decisions live in, and `docs/DOMAIN_GLOSSARY.md` for term definitions.

training offline-capable after onboarding, and puts structured raw sporting data in the
cloud for Free. Its effect on earlier records, without reproducing their contents:

| [0018](0018-indexeddb-production-activation-fencing-and-outage-policy.md) | **Proposed. Incomplete design.** The attempted answer to ADR-0017 Decision 3's bundled prerequisite — resolves **neither** half. Decision 13 row 0b is narrowed, not closed: a proposed `localStorage` Activation Ledger, corrected to be established as a barrier *before* IndexedDB evidence finalizes (never as a best-effort write after), catches an ordinary witness loss while IndexedDB is unreachable. Old-build/tab exclusion is **not resolved** either — a Web-Locks presence check, corrected to a single acquisition per tab (querying every historical lock-name version, fail-closed on any request/query failure, never a "safe no-op" when Web Locks is unavailable) plus an explicit, honest, unverifiable user confirmation (scoped to this browser's own storage partition, not other devices) is the best achievable design without a backend, and this ADR proves directly why no candidate (staged deployment, service worker, handshake, broadcast, Web Locks alone, a bare session registry, or the presence-check-plus-confirmation itself) can make already-running old JavaScript stop writing — a redesigned server-authoritative backend could make such writes non-authoritative, never prevent the local `localStorage.setItem` call itself. | [0025](0025-application-identity-gate-onboarding-completion-and-trusted-device-state.md) | **Accepted architecture decision. Implementation in progress — the design record preceded implementation; B0.2a-c foundations are now implemented and verified but dormant.** Implements [0024](0024-mandatory-identity-and-free-structured-cloud-foundation.md)'s mandatory identity as a concrete gate. One identity authority: a thin `IdentityProvider`, a single `identityRuntime` composition seam, and one `IdentityTransitionCoordinator` owning **every deliberate identity transition** (including **explicit sign-out**) **and every server-driven invalidation transition**; `useSupabaseAuthController` is retired rather than kept as a second orchestrator. Session restoration is classified into **five** outcomes using the SDK's typed predicates, because a transient offline failure and a definitive revocation both surface as a null session with an error. **No raw provider auth event can open the application** — necessary because `exchangeCodeForSession` and `verifyOtp` both persist the session and emit `SIGNED_IN` *before* they resolve. Startup runs **Phase 0 (OAuth return intake) → Phase A (durable preflight, no identity yet) → Phase B (identity binding)**; a legitimate full-page Google return is the intentional continuation mechanism, not a lost one. A durable **`IdentityAccessBarrier`** is **resolved, never deleted** — a deliberate transition writes it before any provider call, navigation or persistent local mutation, while a server-driven invalidation denies in memory first and then attempts it, falling back to trusted-record removal if that write fails — the resolution lives under a key derived from that exact `barrierId`, so an older operation cannot resolve or remove a newer barrier, a property the `get`/`set`-only storage interface cannot otherwise provide. Barrier + attempt + resolution form one durable correlation set that survives reload. Revalidation happens at **named checkpoints**, including one after the resolution write, and **cross-tab atomicity is explicitly not overclaimed**. `identityGeneration` has a live in-memory role and a separate durable role, with **two live epochs across the Google redirect**; the account scope, not any generation, is the cross-reload binding. Google requires a **callback-carried `sb_flow_id` selector** (PKCE + `experimental.appendPkceFlowIdToRedirects`) with **no fallback**, because a flow-less exchange uses the most recent verifier and a failed exchange removes the verifier it selected. Callback capture is **page-scoped, single-use and React-Strict-Mode-safe** — cleaning the URL in a discarded effect pass must not lock out the committed one. Account-scope divergence splits into **correlated replacement (not an invalidation)**, **unexpected mismatch (invalidation)** and **no-session-with-trusted-record**; definitive online denial denies in memory first and **attempts** a durable invalidation barrier before trusted cleanup, and a double failure is reported honestly rather than claiming durable offline revocation. `ensure_my_profile()` is the only bare-Profile creation path; `complete_personal_onboarding()` is **completion-first and write-once**, atomically establishing display name, both pinned legal evidence rows, Athlete capability, the default Free entitlement and the completion fact, or none of them. Legal metadata is immutable and versioned, retirement is one-way, display and submission come from **one snapshot**, an invalid response fails closed as a whole, and **a later document change never auto-revokes a completed Profile**. **B0.2 collects no Marketing Consent, and absence never means consent.** A narrowly scoped removable-storage capability is added for identity records only — **superseding `docs/PERSISTENCE_BOUNDARY_DESIGN.md` §9's "no `remove` operation is needed"** and narrowing [0013](0013-application-owned-persistence-repository-boundary.md)'s adapter contract — but it is **not** the barrier-safety mechanism. Browser storage remains **not a security boundary**: a forged trusted/barrier/attempt/resolution record can mount the shell and expose the still-unscoped local workspace, which is an independent reason **B0.2 and B0.3 are one releasable privacy unit and B0.2 is never independently release-ready** |
